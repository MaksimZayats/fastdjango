<Subtitle>Start from the change you need, not from the layer names.</Subtitle>

Start from the project command or public guide that owns the change. A persisted HTTP feature still
crosses a use case, adapter, migration, controller, composition, and tests, but it does not require a
stack of agent skills.

## Common combinations

### A framework-neutral domain action

Create or inspect the use case through `specx project`; extract a service only if the action contains
reusable behavior. Mirror each behavior module in unit tests and resolve targets from the container.

### A persisted FastAPI endpoint

Use the architecture, persistence, delivery, composition, settings, and testing guides for their
respective parts. The use case owns the transaction boundary; the controller owns HTTP mapping.

### An external API integration

Define a business-language gateway and its technical adapter. Keep credentials and endpoints at the
settings/composition edge. Inject the gateway port into core code, not the SDK client or settings.

### An existing service with mixed boundaries

Map the current structure before moving files. Add the Python package, configure a small selector
set, fix violations by boundary, then broaden selection. See
[Adopt specx in an existing service](/docs/guides/adopt-specx-in-an-existing-service/).

## Choose the narrowest abstraction

Use repository ports for owned persistence and gateway ports for outbound business effects. Model a
narrow replaceable non-IO ability as a capability; keep a local pure implementation detail as a
function when it needs no project class category.
